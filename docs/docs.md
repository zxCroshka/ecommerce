# ТЗ: E-Commerce платформа на Go

---

## Общее описание

Платформа представляет собой backend для интернет-магазина с микросервисной архитектурой. Клиент (мобильное приложение или веб-фронтенд) общается исключительно через API Gateway. Сервисы общаются между собой через gRPC и Kafka. Все сервисы упакованы в Docker.

---

## Роли пользователей

Система поддерживает две роли: `customer` (покупатель) и `admin` (администратор магазина). Роль назначается при регистрации и хранится в JWT токене. Администратор может управлять товарами и просматривать все заказы. Покупатель может просматривать каталог, управлять своей корзиной и создавать заказы.

---

## Сервис 1: User Service

### Регистрация
- Пользователь передаёт `email`, `password`, `name`.
- Email должен быть уникальным. Если такой уже есть — вернуть ошибку `409 Conflict`.
- Пароль хранится только в виде bcrypt-хэша, минимальная длина пароля — 8 символов.
- После успешной регистрации сервис публикует событие `user.registered` в Kafka с полями `user_id`, `email`, `name`.
- Новому пользователю автоматически присваивается роль `customer`.

### Авторизация
- Пользователь передаёт `email` и `password`.
- При успехе сервис возвращает `access_token` (TTL 15 минут) и `refresh_token` (TTL 7 дней).
- `refresh_token` сохраняется в Redis с ключом `refresh:{user_id}:{token_id}`.
- Неверный пароль или несуществующий email — всегда возвращать одинаковую ошибку `401 Unauthorized` (не раскрывать, что именно неверно).

### Обновление токена
- Клиент передаёт `refresh_token`.
- Сервис проверяет его наличие в Redis. Если его нет — токен инвалидирован, вернуть `401`.
- При успехе выдаётся новая пара токенов, старый `refresh_token` удаляется из Redis (ротация токенов).

### Logout
- Сервис удаляет `refresh_token` из Redis.
- `access_token` добавляется в чёрный список в Redis с TTL равным оставшемуся времени жизни токена.

### Профиль
- Авторизованный пользователь может получить и обновить свои `name`, `email`.
- Смена пароля — отдельный эндпоинт, требует передачи старого пароля для подтверждения.

### gRPC (внутренний)
- `ValidateToken(token)` — проверяет подпись JWT и чёрный список в Redis, возвращает `user_id` и `role`.
- `GetUser(user_id)` — возвращает базовые данные пользователя для других сервисов.

## Сервис 2: Product Service

### Каталог товаров
- Товар имеет поля: `id`, `name`, `description`, `price`, `stock` (остаток на складе), `category`, `images` (массив URL), `is_active`, `created_at`.
- Получение списка товаров поддерживает фильтрацию по `category`, сортировку по `price` и `created_at`, пагинацию (limit/offset).
- Выдавать только товары с `is_active = true` для покупателей.
- Список товаров кэшируется в Redis на 5 минут. При изменении любого товара кэш инвалидируется.

### Управление товарами (только admin)
- Создание, редактирование, удаление (мягкое удаление через `is_active = false`) товаров.
- При изменении цены или остатка публиковать событие `product.updated` в Kafka.

### Остатки
- При создании заказа Order Service вызывает gRPC метод `ReserveStock(product_id, quantity)`.
- Если товара недостаточно — возвращать ошибку. Резервирование должно быть атомарным (использовать транзакцию в PostgreSQL).
- При отмене заказа Order Service вызывает `ReleaseStock(product_id, quantity)` — остаток возвращается.



### gRPC (внутренний)
- `GetProduct(product_id)` — получить данные товара.
- `ReserveStock(product_id, quantity)` — зарезервировать остаток.
- `ReleaseStock(product_id, quantity)` — освободить резерв.

## Сервис 3: Cart Service

### Корзина
- Корзина хранится целиком в Redis как hash с ключом `cart:{user_id}`, поле — `product_id`, значение — `quantity`.
- TTL корзины — 7 дней. Обновляется при каждом изменении.
- Добавление товара: если товар уже есть — увеличить количество. Если `quantity = 0` — удалить позицию из корзины.
- Перед добавлением товара в корзину сервис вызывает `GetProduct` у Product Service через gRPC, чтобы убедиться что товар существует и активен.
- Количество одного товара в корзине не может превышать 99.

### Оформление заказа
- При оформлении заказа Cart Service возвращает содержимое корзины Order Service и очищает её.
- Если корзина пуста — вернуть ошибку `400 Bad Request`.

## Сервис 4: Order Service

### Создание заказа
- Клиент инициирует создание заказа. Order Service получает корзину из Cart Service через gRPC.
- Для каждой позиции вызывает `ReserveStock` у Product Service. Если хотя бы один товар недоступен — весь заказ отклоняется, уже зарезервированные позиции освобождаются.
- Заказ сохраняется в PostgreSQL со статусом `pending`.
- После успешного сохранения публикуется событие `order.created` в Kafka с полями `order_id`, `user_id`, `items`, `total_price`.
	
### Статусы заказа
Заказ проходит строго по цепочке: `pending` → `confirmed` → `shipped` → `delivered`. Отмена (`cancelled`) возможна только из статусов `pending` и `confirmed`.

При смене статуса публикуется событие `order.status_changed` в Kafka.

При отмене заказа Order Service вызывает `ReleaseStock` у Product Service для каждой позиции.

### Просмотр заказов
- Покупатель видит только свои заказы.
- Администратор видит все заказы с возможностью фильтрации по статусу и дате.

## Сервис 5: Notification Service

### Подписки на события Kafka
Сервис слушает три топика и отправляет email уведомления:

- `user.registered` → приветственное письмо с подтверждением регистрации.
- `order.created` → письмо с деталями заказа и итоговой суммой.
- `order.status_changed` → письмо об изменении статуса заказа.

### Требования к надёжности
- Каждое событие должно быть обработано ровно один раз. Для этого хранить в PostgreSQL таблицу `processed_events` с `event_id`. Перед обработкой проверять, не было ли событие уже обработано.
- Если отправка письма упала — повторить попытку до 3 раз с экспоненциальной задержкой (1с, 2с, 4с). После трёх неудачных попыток записать событие в таблицу `failed_events` для ручной проверки.
- На старте использовать mock-отправку (просто логировать письмо в консоль). Реальный SMTP подключается через переменную окружения.

## API Gateway

- Единственная точка входа для всех внешних запросов.
- Для каждого входящего запроса вызывает `ValidateToken` у User Service через gRPC. Если токен невалиден — возвращает `401` не пропуская запрос дальше.
- Проксирует запрос в нужный сервис на основе пути.
- Rate limiting: не более 100 запросов в минуту с одного IP, хранить счётчики в Redis.
- Все запросы логируются с полями: `request_id`, `user_id`, `method`, `path`, `status`, `latency`.

---

## Общие технические требования

- Каждый сервис имеет эндпоинт `GET /healthz` который возвращает `200 OK` — используется Docker для проверки состояния контейнера.
- Все конфигурации (порты, строки подключения, секреты) передаются через переменные окружения, никаких захардкоженных значений.
- Миграции базы данных запускаются автоматически при старте сервиса через `golang-migrate`.
- Логирование через `zerolog` или `zap` в формате JSON.
- Каждый сервис покрыт unit-тестами на уровне сервисного слоя с моками репозитория.
